# Feature Specification: Analyze and Log a Vacancy in One Pass

**Feature Branch**: `009-analyze-and-log-vacancy`

**Created**: 2026-08-04

**Status**: Draft

**Input**: User description: "Analyze a posting should accept an uploaded document (not just
pasted text) - same formats already supported for logging a vacancy (image, PDF, DOCX, plain
text). When a document is uploaded on the Analyze screen, the user sees both the match report
AND drafted company/position/date fields together in one view, and can confirm the outcome
right there to save it as a logged vacancy - no separate visit to the Log a vacancy screen
required for this case. Pasting text stays supported for when there's no document to upload (a
match report only, since there's nothing to draft company/position/date from or log)."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Analyze a posting from the document you already have (Priority: P1)

A user has the job posting as a file — a PDF, a screenshot, a DOCX, or a plain-text export —
rather than something they'd copy-paste. Today they'd have to manually extract and paste the
text (or can't, for an image) before they can get a match report. They should be able to upload
the file directly on the Analyze screen and get the same match report they'd get from pasting
its text.

**Why this priority**: Without this, the Analyze screen simply doesn't work for the very common
case of "I have this posting saved as a file" — it's the precondition for everything else in
this feature.

**Independent Test**: Upload a real posting document (each of image/PDF/DOCX/text) on the
Analyze screen and confirm a match report (score, flags, gaps, similar vacancies, draft
paragraph) appears, matching what pasting the equivalent text would produce.

**Acceptance Scenarios**:

1. **Given** the Analyze screen, **When** a user uploads a PDF/DOCX/text posting instead of
   pasting text, **Then** they see the same kind of match report as the paste flow produces.
2. **Given** the Analyze screen, **When** a user uploads an image of a posting, **Then** they
   see a match report generated by the configured backend reading the image directly (no local
   OCR), consistent with how image-based drafting already works for logging a vacancy.

---

### User Story 2 - Save the vacancy right where you analyzed it (Priority: P2)

After uploading a document and seeing the match report, a user who wants to log this vacancy
(with an outcome) shouldn't have to separately go to the Log-a-vacancy screen and upload the
same file a second time. Company/position/date should already be drafted from the same upload,
shown alongside the report, ready to review and save.

**Why this priority**: This is the actual time-saving payoff of accepting an upload on the
Analyze screen — without it, User Story 1 alone would still leave a duplicate-upload step for
anyone who wants to log the vacancy, which is the exact friction this feature exists to remove.

**Independent Test**: After uploading a document and seeing the match report, edit the drafted
company/position/date, type an outcome, and save — confirm a new vacancy folder is created and
is immediately searchable, without visiting the Log-a-vacancy screen or re-uploading anything.

**Acceptance Scenarios**:

1. **Given** a document was uploaded and a match report is showing, **When** the user looks at
   the same screen, **Then** they also see company/position/date fields pre-filled from that
   same document, editable, with an outcome field to fill in.
2. **Given** the drafted fields and a typed outcome, **When** the user confirms, **Then** a new
   vacancy folder is written and embedded immediately — the same outcome as today's
   Log-a-vacancy confirm step.
3. **Given** drafting the fields failed for this upload (e.g. the backend couldn't read it) but
   the match report succeeded, **When** the user looks at the screen, **Then** the match report
   is still fully shown, and the fields are present but empty/editable with a message explaining
   drafting didn't work — the report is never held back by a drafting failure, or vice versa.

---

### User Story 3 - Pasting text still just gives a report (Priority: P3)

A user with no document — just text they've copied — pastes it as before. They should get
exactly the match report they get today, with no half-functional draft/save controls shown,
since there's no source document to draft fields from or to log.

**Why this priority**: Lowest priority because it's preserving existing behavior, not adding
new value — but it matters that adding the upload option doesn't degrade or confuse the
paste-text path that already works.

**Independent Test**: Paste job posting text (no file) and confirm only the match report
appears — no draft fields, no save controls, nothing implying a vacancy could be logged from
this submission.

**Acceptance Scenarios**:

1. **Given** the Analyze screen, **When** a user pastes text and submits, **Then** they see only
   the match report, unchanged from today's behavior.

---

### Edge Cases

- Uploading a document whose company/position/date exactly matches a vacancy already logged —
  the same "already exists" conflict message as today's Log-a-vacancy confirm should appear when
  the user tries to save.
- Uploading a document type or format the configured backend can't analyze or draft from (e.g.
  no vision support for images) — the affected part (report and/or draft) shows a specific,
  honest message instead of silently failing or guessing; the other part still works
  independently if it can.
- A user uploads a document, sees the report, but leaves without saving — no vacancy folder is
  created, exactly like today's "never confirming creates no vacancy folder" behavior.
- The configured LLM provider is missing required configuration entirely (e.g. no API key set
  for a hosted backend) — this is a setup problem, not a per-request failure, and should be
  caught once, up front, rather than surfacing as a confusing failure on the first report or
  draft a user attempts.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The Analyze screen MUST allow uploading a document (image, PDF, DOCX, or plain
  text — the same formats already accepted for logging a vacancy) as an alternative to pasting
  text.
- **FR-002**: When a document is uploaded, the system MUST produce the same kind of match report
  (score, flags, gaps, similar vacancies, draft opening paragraph) that pasting the equivalent
  text would produce.
- **FR-003**: When a document is uploaded, the system MUST also draft company/position/date from
  that same document, using the same drafting capability already used on the Log-a-vacancy
  screen.
- **FR-004**: The match report and the drafted company/position/date fields MUST appear together
  in one view when a document was uploaded — not as two separate steps requiring a second
  upload.
- **FR-005**: From that combined view, the user MUST be able to edit the drafted fields, type an
  outcome, and save the vacancy — writing a new vacancy folder and making it immediately
  searchable — without leaving the screen or re-uploading the document.
- **FR-006**: When the user pastes text instead of uploading a document, the system MUST show
  only the match report — no draft fields and no save option.
- **FR-007**: A failure drafting company/position/date for an uploaded document MUST NOT prevent
  the match report from being shown, and a failure generating the match report MUST NOT prevent
  an independently-successful draft from being reviewed and saved — each shows its own
  plain-language failure message without blocking the other.
- **FR-008**: Saving a vacancy from the Analyze screen MUST behave identically to today's
  Log-a-vacancy save (same required fields, same duplicate/conflict handling, same immediate
  searchability) — this feature adds a second place to reach that outcome, not a second
  behavior for it.
- **FR-009**: The existing Log-a-vacancy screen MUST remain available and unchanged, for logging
  a vacancy without necessarily running a match-report analysis on it.
- **FR-010**: The system MUST validate, before it starts accepting requests, that required
  configuration for the configured LLM provider is present (e.g. an API key for a hosted
  backend) — if it is missing, the system MUST refuse to start and state specifically what is
  missing, rather than starting normally and failing later, mid-request, with an opaque error.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A user with a posting saved as a PDF, DOCX, image, or text file gets a match
  report without first manually extracting or retyping its text.
- **SC-002**: A user can go from uploading a posting document to a saved, logged vacancy (with a
  typed outcome) in one screen, without visiting a second screen or uploading the file twice.
- **SC-003**: Pasting text with no document continues to produce a match report exactly as
  today, with no draft or save controls shown.
- **SC-004**: A drafting failure never hides an otherwise-successful match report, and a
  report-generation failure never hides an otherwise-successful draft.
- **SC-005**: A user who forgets to set a required credential for their configured LLM provider
  finds out immediately, in one specific message, instead of discovering it partway through
  their first report or draft attempt.

## Assumptions

- The existing Log-a-vacancy screen (upload → draft → review → confirm, with no match-report
  analysis) stays unchanged and available as a separate, simpler path — this feature adds
  analysis on top of an upload, it does not remove or replace the logging-only path.
- Image uploads are expected to support match-report analysis using the same vision capability
  already used for image-based drafting (specs/007-vision-drafting) — if the configured LLM
  backend can't do vision-based analysis, the user sees a specific, honest message rather than a
  silent fallback, consistent with how image drafting already handles that case.
- "Same formats already supported for logging a vacancy" means image (`.png`/`.jpg`/`.jpeg`),
  PDF, DOCX, and plain text (`.txt`/`.md`) — the exact set the existing upload already accepts.
- The match report itself is not newly persisted to the vacancy folder as part of this feature —
  saving still writes only company/position/date/outcome (plus the source document), exactly as
  today's confirm step already does.
